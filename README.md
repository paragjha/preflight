# PreFlight

Catch listing errors *before* they reach the marketplace. Upload a partner's
.xlsx, get a per-row verdict (schema + semantic), review anything ambiguous,
re-run with the corrections folded in, and export a clean sheet ready to
upload. Optional: hand PreFlight the marketplace's own template and it
generates its own rulepack — no per-customer config project.

## Quick start

```powershell
cd preflight
pip install -r requirements.txt

# get a free key at https://aistudio.google.com/apikey
cp .env.example .env    # then edit .env and paste your GEMINI_API_KEY
python generator.py                              # writes demo_batch.xlsx + demo_template.xlsx
python -m uvicorn app:app --host 127.0.0.1 --port 8021
# open http://127.0.0.1:8021/
```

Then in the browser:

1. **New batch** → drop a .xlsx → pick region → **Preflight this batch**
   (or click **Load demo batch** for the bundled 60-row sample).
2. **YOUR MARKETPLACE TEMPLATE → Load template** (optional): hand it any
   marketplace's own upload template and PreFlight extracts the rulepack —
   required columns from the header colouring, per-column enums from the
   dropdown validations, per-category size-units from an optional `Config`
   sheet. Every future batch under this tenant validates against it.
3. Click any row for the drawer; review semantic flags as
   `confirmed_error` or `false_positive` (fed to memory).
4. **Errors ↓** downloads a plausible cataloging-tool error sheet built
   from this batch's own rejected rows. **Errors ↑** feeds it back in
   as `confirmed_error` corrections. That's the *"the system that rejects
   you becomes the system that trains you"* loop, playable without a real
   validator.
5. **Re-run semantic** folds all corrections in.
6. **Export corrected sheet** downloads the upload-ready xlsx — canonical
   column order, red fill on cells that still need fixing, trailing
   `preflight_status` column (`ready` / `fix_required` / `review`).

## Layers

| Layer | Where | What it catches |
|---|---|---|
| Schema (row-local) | `validate_schema.check_schema` | required, format, GTIN checksum, enum, region; deterministic, autofixes what's safe |
| Schema (cross-row, v2) | `validate_schema.check_cross_row` | `DUPLICATE_GTIN`, `DUPLICATE_SKU` within a batch — solves the "valid checksum, copied from another row" trap |
| Semantic | `semantic.py` (one LLM call) | title↔brand duplication, title↔size contradiction, unit plausibility per category, description↔attribute contradiction |
| Memory (v2, multi-tenant) | `memory.py` + `data/tenants/<tenant>/corrections.json` | human verdicts fed back as few-shot on the next run; scoped per customer |
| Rulepack (v2) | `template.py` + `data/tenants/<tenant>/rulepack.json` | marketplace template becomes a rulepack: required columns, enum values, category→size-units |

Model: **`gemini-flash-latest`** via Gemini's OpenAI-compatible endpoint
(swap `MODEL_ID` at the top of `semantic.py` to change).

## Numbers from the demo batch

Generated by `python generator.py` (60 rows: 30 clean, 18 schema-broken,
12 semantic traps — one of which, r060, is a cross-row duplicate GTIN).
Scored by `python proof.py` against `demo_batch.answer_key.json`. Every
number below is pasted from an actual run — nothing rounded.

| Metric | Result | Target |
|---|---|---|
| Row-local schema layer caught | **18 / 18** rows with hard errors | 18 / 18 |
| Cross-row schema (v2) caught | **r001 + r060** duplicate-GTIN pair | pair flagged |
| Semantic layer caught (initial run) | **11 / 12** traps | ≥ 9 / 12 |
| Total trap catch rate incl. cross-row (v2) | **12 / 12** | — |
| False positives on 30 clean rows | **0 / 30** | ≤ 2 |
| Learning loop (re-run after review) | **r049 + r050 suppressed** after marking r049's `TITLE_BRAND_MISMATCH` as `false_positive`; the 9 other semantic traps still caught | flag disappears |
| Unit tests | **40 passed** | all green |

The v1 miss (r060, duplicate GTIN) is now caught deterministically by the
cross-row checks added in v2 — the model was never going to see other
rows, so that's the right layer for it.

**Reproducibility note:** the free tier for `gemini-flash-latest` has a
~500 requests-per-day cap. A day of heavy iteration (upload + review +
rerun cycles + `proof.py --learn` runs = ~6 calls each) can exhaust it,
and further runs come back as `semantic_status: "partial"` or `"failed"`
until the quota rolls over. That is a *reporting* condition, not a code
bug: the batch is stamped, `silent_errors_found` / `clean` come back as
`null`, the UI shows a warning banner with the underlying `HTTP 429`
detail, and re-running `proof.py --learn` the next day produces the
numbers in the table.

## Reliability

- **Semantic-layer failures don't read as success.** If any batch of LLM
  calls fails (429, timeout, malformed JSON both attempts), the batch is
  stamped `semantic_status: "partial"` or `"failed"` and the
  `silent_errors_found` / `clean` metrics come back as `null` (rendered
  "—" in the UI). A dashed number never means "zero problems"; it means
  "we couldn't measure."
- The underlying error (HTTP status + first 200 chars of body, or exception
  type) is captured on the batch as `semantic_error_detail` and printed to
  the server log. No guesswork required.
- A single 429 auto-retries once with backoff parsed from the API's own
  `retry-after` hint (capped at 60s).

## v2 additions in one paragraph

Four things landed on top of v1: **multi-tenant memory** — corrections now
live under `data/tenants/<tenant>/corrections.json`, so different customers'
learning stays separate; **template ingestion** — hand `POST /api/tenants/{tenant}/rulepack`
a marketplace's own .xlsx template and PreFlight extracts required columns
(from header fill colour), enums (from data-validation dropdowns), and
per-category size units (from an optional `Config` sheet); **error-sheet
learning loop** — `POST /api/batches/{id}/errors` reads the validator's
returned error sheet and folds each rejection into memory as a
`confirmed_error` correction (matching by row_id, then partner_sku, then
GTIN); **cross-row uniqueness** — `DUPLICATE_GTIN` and `DUPLICATE_SKU`
schema checks catch the "valid checksum, copied from another row" trap
the row-local pipeline can't see.

## Repo layout

```
preflight/
  app.py             FastAPI routes (thin — logic lives in the modules below)
  ingest.py          xlsx -> canonical rows (header synonym mapping)
  schema_def.py      the single source of truth for fields/categories/regions
  validate_schema.py deterministic checks + safe autofixes + cross-row uniqueness (v2)
  semantic.py        one LLM call, batched, memory-aware, honest about failures
  memory.py          per-tenant corrections store (v2)
  metrics.py         row verdicts + the pitch numbers
  export.py          xlsx export (canonical column order, red fill on rejects)
  template.py        v2: marketplace .xlsx template -> rulepack
  errors.py          v2: validator error sheet -> memory corrections
  gtin.py            GS1 check-digit
  generator.py       makes the 60-row demo batch + answer key + demo template
  proof.py           runs the pipeline end-to-end and scores vs the answer key
  static/            index.html + opal.css (Opal design system)
  data/              batches, tenants (corrections + rulepacks), sku_counters (gitignored)
  tests/             40 unit tests, pytest
```

## API surface

| Method | Path | What |
|---|---|---|
| POST   | `/api/batches` (multipart `file`, `region`, optional `tenant`) | upload → schema → semantic → persist |
| POST   | `/api/batches/demo` (`region`, `tenant`) | one-click load of the bundled `demo_batch.xlsx` |
| GET    | `/api/batches` | list summaries |
| GET    | `/api/batches/{id}` | full batch JSON |
| GET    | `/api/batches/{id}/metrics` | the 8 pitch numbers + `semantic_status` |
| POST   | `/api/batches/{id}/rows/{row_id}/review` | record human verdict on a semantic flag |
| POST   | `/api/batches/{id}/rerun` | re-run semantic layer with current memory |
| GET    | `/api/batches/{id}/export` | download upload-ready `<name>_preflight.xlsx` |
| POST   | `/api/batches/{id}/errors` (multipart) | *v2* — validator error sheet → memory |
| GET    | `/api/batches/{id}/simulated_errors` | *v2* — download plausible error sheet from this batch's own rejects |
| POST   | `/api/tenants/{tenant}/rulepack` (multipart) | *v2* — upload marketplace template |
| GET    | `/api/tenants/{tenant}/rulepack` | *v2* — inspect stored rulepack |
| DELETE | `/api/tenants/{tenant}/rulepack` | *v2* — clear tenant's rulepack |

Stack: Python 3.11+, FastAPI, uvicorn, openpyxl, httpx, python-multipart
(transitive for FastAPI Form/File). No pandas, no DB, no ORM, no build
chain. Frontend is one HTML + one CSS + inline JS; no bundler.

## What v3 would be

The build spec's v3 line is: *"own the intake — watches inbox, parses
incoming requests, assembles the sheet, routes category-manager approval,
assigns itself the work"*. Everything above `POST /api/batches` becomes
inbox-triggered; humans set direction and approve escalations. That's
integration work (email, approval flow) — the judgment core is what's
already here.
